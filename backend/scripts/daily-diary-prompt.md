规则：
- 没证据就不写；用户计划不写成已完成，Agent 推断不写成用户事实。
- 每条关键结论末尾用简短证据标签：`[用户明确]`、`[Agent 汇报]`、`[Git]`、`[自动化日志]`、`[活跃工单]`、`[昨日对照]`。assistant 最终回复只能标为 `[Agent 汇报]`；只有 commits 和 automationEvents 才能标为代码或日志验证。
- 合并重复内容，保留具体结果、验证方式和仍未解决的问题；不要复述授权卡、测试口令或聊天寒暄。
- 工作日记要像长期协作者写给用户：说明变化和意义，但不编造心理、情绪或动机；不要写成流水账或审计清单。
- “是否值得长期记住”默认写“暂无新增候选”。只有当天 Git 提交直接证明的稳定工作流迁移、用户明确作出的重大决策，或多次独立任务反复验证的经验，才列候选并说明证据。
- 普通 Bug、权限位、路径、部署细节、一次性排障、单次内容改稿和仍在影子验证的方案不列候选。本次绝不自动写 memory、ADR 或 process-log。
- 自动化日志只用于佐证状态，噪音、重复行和不完整片段不要照抄。
- “明天接着做”和 HANDOFF 的“下一步依据”严格按：用户明确下一步 > continuity.activeHandoffs > 已批准未完成 > 自动化阻塞。模型自己的建议只能放在最后并标 `[建议]`，不能冒充既定任务。
- HANDOFF 增量只写今天相对真相源发生的变化，不复制项目介绍；`不要误判`专门记录影子运行不等于正式切换、Agent 汇报不等于系统验证等边界。
- 内容精炼，以事实密度和连续性优先，禁止编造“能长出的选题”。
